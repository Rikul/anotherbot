# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a Python-based AI agent ("anotherbot") that uses an OpenAI-compatible API (defaulting to OpenRouter/DeepSeek) via the `openai` Python SDK. It supports an interactive terminal UI (`app/cli/tui.py`, prompt_toolkit + rich), single-prompt (`-p`) mode with optional `--quiet` console logging, and a background server architecture with Telegram, Discord, and a web channel (Starlette JSON/WebSocket API + static `app/channels/frontend/` UI).

## Running & Development

```bash
# Run the CLI agent (interactive terminal UI; plain REPL when not a TTY).
# There is no "cli" subcommand: no command means the CLI agent.
./run.sh

# Run a single prompt and exit (-p always exits after the response)
./run.sh -p "your prompt here"

# Run with auto-approve (no permission prompts)
./run.sh -p "your prompt" -y

# Quiet mode: no log messages on the console (still written to the log file)
./run.sh -p "your prompt" -y -q

# Run tests
uv run pytest

# Run a single test file
uv run pytest tests/test_agent.py

# Run a single test
uv run pytest tests/test_agent.py::test_agent_loop_adds_user_message

# Run integration tests
uv run pytest tests/integration/
```

The project uses `uv` for dependency management. No compile step is needed.

## Configuration

All configuration comes from environment variables — there is no config file. `app/config.py` calls `load_dotenv()` at import time, before computing `PROJECT_HOME`: first the nearest `.env` (searched from `app/` upwards, normally the repo root), then `$PROJECT_HOME/.env`. Neither overrides variables already set in the real environment. `config.load()` (called at the start of `main()`) builds `_config` from defaults + env vars and raises `ValueError` on invalid integers so bad config fails fast. Template: `app/.env.example`.

- `LLM_API_KEY` — required (`config.get("api_key")`)
- `LLM_BASE_URL` — API base URL (default: `https://openrouter.ai/api/v1`)
- `LLM_MODEL` — model string (default: `deepseek/deepseek-v4.1-flash`)
- `MAX_ITERATIONS` — max agentic loop iterations (default: `250`; CLI `-i` overrides)
- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOW_FROM` — bot token and comma-separated user IDs (→ `config.telegram`)
- `DISCORD_BOT_TOKEN`, `DISCORD_ALLOW_FROM` — bot token and comma-separated user IDs; empty = allow all (→ `config.discord`)
- `WEBSOCKET_HOST` — bind host for the web UI; setting it enables the web channel (`0.0.0.0` in Docker)
- `WEBSOCKET_PORT` — port for web UI + WebSocket (default: `8765`)
- `WEB_PASSWORD` — web UI login password (→ top-level `config.get("web_password")`, *not* the `websocket` section, so setting it alone doesn't enable the channel)
- `ANOTHERBOT_HOME` — data directory, `PROJECT_HOME` (default: `~/.anotherbot`). Holds `app.db`, `logs/app.log`, uploads, traces, `mcp_servers.json` and an optional `.env`. Read at import time, so it can be set in the repo-root `.env` but not in `$PROJECT_HOME/.env`.

MCP servers are configured separately in `$ANOTHERBOT_HOME/mcp_servers.json` (same format as Claude Desktop's `mcpServers` key).

For Docker, `compose.yaml` is the easy path (`docker compose up -d --build` reads the repo-root `.env`, forces `WEBSOCKET_HOST=0.0.0.0` and `ANOTHERBOT_HOME=/data`, and publishes `${WEBSOCKET_PORT:-8765}` on both sides). With plain `docker run`, pass env vars with `-e`/`--env-file`. `.dockerignore` excludes `.env` files so secrets are never baked into the image. See `Dockerfile` and the Docker section in README.

## Architecture

### Agent Loop

The shared loop lives in `Agent._loop()` (`app/core/agent.py`). Subclasses override hooks to specialise behaviour:

| Hook | CliAgent | BackgroundAgent | HelperAgent |
|---|---|---|---|
| `_on_thinking` | `ui.thinking` (print without a UI) | send via mq | — |
| `_check_permission` | `ui.ask_permission` (ask stdin without a UI; skipped with `-y`) | — (always allow) | — |
| `_on_tool_start` | `ui.tool_start` | send status via mq | — |
| `_on_response` | `ui.response` (print without a UI) | send via mq | — |
| `_on_no_choices` | raise | exponential backoff | raise |
| `_should_stop` | — | `channel.has_stopped` | — |

Tool calls within a single LLM turn are dispatched in parallel via `asyncio.gather`. After each turn, the full message chain (assistant tool-call message + tool results + final response) is saved to `self.messages` at full length. `MessageHistory` (SQLite) stores only user + final assistant text for cross-session persistence.

**Trajectories.** Agents with `saves_trajectories = True` (`CliAgent`, `BackgroundAgent`; not `HelperAgent`) collect per-call stats (`model`, `duration_s`, `finish_reason`, `usage`) in `_llm_calls` during `_run_loop`, and after each turn `Agent._save_trajectory()` stores the turn in the `trajectories` table (`message_id` PK → the final assistant `messages` row, which `MessageHistory.add_message()` now returns; `conversation_id`; `data` JSON; `created_at`). The JSON holds the system prompt, a history-message count, the turn's own messages (user message, assistant tool calls/reasoning, tool results, final reply; attachment data URLs redacted with `tracer.redact`), the `llm_calls` list and summed `usage_total`. Saving is best-effort (logged, never raised). `ConversationStore.delete()` removes a conversation's trajectories and `fork()` copies them to the new message rows. `BackgroundAgent` then awaits `Channel.on_trajectory_saved(message_id, conversation_id, metadata)` (no-op by default).

### Command Line

`parse_args()` (`app/main.py`) puts every option on the top-level parser; the only subcommand is `background`. With no command, `args.command` is set to `"cli"` and `main()` calls `run_cli()`. `-p`, `-y` and `-i` with `background` are a parser error; `-q`, `--trace` and `--tracedir` apply to both. `max_iterations` falls back to `MAX_ITERATIONS` when `-i` isn't given. `Dockerfile` and `restart.sh` run `run.sh background`.

### Terminal UI

`run_cli()` (`app/cli/cli.py`) starts `run_tui()` (`app/cli/tui.py`) when there is no `-p` and both stdin and stdout are TTYs; otherwise `-p` runs one turn with plain `print()` output and the non-TTY REPL reads lines with `input()` (tests patch `app.cli.cli.input_loop`). The TUI is a full-screen prompt_toolkit `Application` (`Tui.build_app()`): an output `Window` driven by `_OutputControl`, a busy line (spinner, activity, elapsed, queued count) while a turn runs, a rule, the permission bar *or* the input `Buffer` window (pinned to the bottom, 1–12 lines, `SearchToolbar` for Ctrl+R), a rule and the status bar, plus a `CompletionsMenu` float. Output is rich renderables kept in a `Transcript` (`app/cli/tui_text.py`, with the text helpers and `TuiCompleter`): each block is rendered by a rich `Console` (StringIO, truecolor) at the pane width into ANSI, parsed to prompt_toolkit fragments and split into lines; a width change re-renders all blocks; only the last `max_blocks` (2000) are kept. `_OutputControl` is bottom-anchored: `Tui.scroll_up` (PageUp/PageDown; Up/Down stay prompt history) is the offset from the end. There is no mouse capture (it would block the terminal's own text selection and Ctrl+wheel zoom), and `run()` writes `ALT_SCROLL_OFF` (DEC 1007 reset) before the app starts and `ALT_SCROLL_ON` on exit, so terminals that turn the wheel into Up/Down keys in the alternate screen don't step through prompt history, and it puts the cursor on the last visible line and returns the matching `get_vertical_scroll`. `Tui.print()` appends and invalidates; `print_threadsafe()` is for log records from tool threads. `submit()` puts input on `_inbox`; `_worker()` runs messages and commands one at a time via `handle_input()`, so input typed during a turn is queued. On startup and whenever a command switches conversations, the pane is cleared and `show_conversation()` shows the header and up to `_HISTORY_ON_OPEN` messages. `Tui` owns a `CliAgent(ui=self)`: with a `ui`, `CliAgent` routes its hooks (`thinking`, `tool_start`, `tool_result` — via a `handle_tool_call` override — `response`, async `ask_permission`) to the UI instead of printing/`input()`. Permission prompts are serialised by an `asyncio.Lock` (tool calls run in parallel); `_read_permission_key()` awaits a future that the permission-mode key bindings resolve through `answer_permission()` (the input buffer is read-only meanwhile, and answer keys within `_PERMISSION_GRACE_SECS` of the prompt appearing are ignored so typing can't answer it); answers (`y`/`n`/`a`/`!`, Ctrl+C; never Enter, which also sends messages, nor Escape): yes / no / always for this tool (`allowed_tools`) / approve all / interrupt. Ctrl+C is a key binding (`on_ctrl_c`, raw mode, no SIGINT): it answers a pending prompt with interrupt, else cancels the running turn task, else clears the input, else arms/quits. On cancellation `CliAgent.agent_loop` stores `INTERRUPTED_REPLY` as the assistant message so the DB and `self.messages` stay consistent. Sync tools run in a thread (see Tool System), so the screen and Ctrl+C stay live; `bash` is async and Ctrl+C kills a running command. All model/tool text goes through `clean()` (strips C0/C1 control characters, so no escape sequence from tool output reaches the terminal). `@path` tokens naming existing files become `metadata["files"]` attachments (`extract_attachments`). Input history is `$ANOTHERBOT_HOME/cli_history`. Console logging is replaced by `_ConsoleLogHandler` (warnings and up, shown in the pane); the log file is unchanged.

### Tool System

Each tool is a class extending `Tool` (`app/core/tool.py`), an ABC requiring a static `spec()` (OpenAI function-call schema) and a static `call()` taking the parameters declared in `spec()` (sync or async). Because `call` signatures differ per tool, `call` is declared as an attribute rather than an abstract method and checked in `Tool.__init_subclass__`. Tools are registered in `app/core/tool_calls.py` in `tool_registry` — a dict mapping tool name → `Tool` class. `run_tool()` is asynchronous and dispatches by name: it awaits the tool's `call` if it is a coroutine function and otherwise runs it in a worker thread (`_run_in_thread` → `_start_daemon_thread`: like `asyncio.to_thread`, context copied, but a daemon thread so quitting never waits for a hung cancelled tool; a slow tool doesn't block other channels or the TUI). Threaded tools run one at a time (an `asyncio.Lock`, created per event loop), as they did when they blocked the loop, so parallel calls from one turn (two `write_file`s to one path) can't overlap. Async tools with `exclusive = True` (`bash`, which blocked before it became async) take the same lock (`_run_exclusive`); other async tools (MCP, `helper_agent`) run concurrently, as before. A thread can't be stopped, so when the caller is cancelled `_run_in_thread` re-raises at once (Ctrl+C stays immediate) and records the still-running thread in `_unfinished`; every later tool call (`run_tool` and MCP calls in `run_tool_async`) first awaits `_wait_for_unfinished()`, so a cancelled tool's side effects never overlap a later tool's. That wait is capped at `UNFINISHED_WAIT_SECS` (60 s) counted from when the call was cancelled (`_unfinished_since`), not restarted per call: once the oldest unfinished thread is past it, every call returns an error to the model at once instead of running, so a hung thread can't stall later tool calls in any channel. A thread still running `UNFINISHED_ABANDON_SECS` (300 s) after its cancel is abandoned (`_abandon_stale`, logged as an error): it stops blocking, so a thread stuck forever can't disable tools until a restart. While any is tracked, the TUI status bar shows "⚠ <tool> still running". The TUI names such tools after "Interrupted" (`unfinished_tools()`). Tools with `runs_in_thread = False` (the todo tools, which share an unlocked in-memory list) run on the loop instead. `bash` is async (`asyncio.create_subprocess_shell` in a new session on POSIX / new process group on Windows, stdin `/dev/null`) and kills the whole group (`killpg` / `taskkill /T /F`) on timeout or cancellation. A new session has no controlling terminal, so commands that prompt (sudo, ssh/git passwords) fail fast instead of hanging; the tool description tells the model to use non-interactive flags. (`process_group=0` would keep the terminal but put the shell in a background group, where a terminal read stops it with SIGTTIN until the timeout.) `run_tool` restores `os.getcwd()` after execution. Results are truncated to `MAX_TOOL_RESULT_LENGTH` (16 000 chars, defined in `app/core/tool.py` so `mcp_manager` can use it without importing `tool_calls`).

Current built-in tools: `read_file`, `write_file`, `bash`, `list_dir`, `glob`, `grep`, `git_status`, `git_diff`, `git_log`, `web_fetch`, `use_skill`, `todo_add/list/update/clear`, `calculator`, `hackernews`, `websearch_text/images/videos/news/books`, `list/add/update/remove_scheduled_task`, `get_scheduled_task_output`, `get_city_state`, `get_datetime`, `helper_agent`, `save_memory`, `search_memory`, `delete_memory`.

**Read-only tools.** `Tool.read_only = True` marks tools that only read local state and run no program from it: `read_file` (regular files only, at most `MAX_READ_BYTES` (1 MB) per call, with a note giving the next offset), `list_dir`/`glob`/`grep` (`app/tools/fs_search.py`, pure Python; glob/grep skip `SKIP_DIRS` such as `.git`, `node_modules`, `.venv` and stop after `WALK_TIME_BUDGET_SECS` (20 s, threaded tools share one lock); grep reads only regular files (a FIFO or `/dev/zero` would hang) and shows a long line as a `MAX_GREP_LINE` window around the match with `[match at col N of M]`; all three stay under `OUTPUT_BUDGET` (`_join_within_budget`: below `MAX_TOOL_RESULT_LENGTH`, so the closing "… more" notes are never the part cut off); a glob without `/` matches the file name at any depth) and `git_status`/`git_diff`/`git_log` (`app/tools/git_tools.py`). They exist so the model stops running `ls`/`find`/`grep`/`git status|diff|log` through `bash`; each takes a `path` instead of `cd`. The git tools run `git` without a shell, with `GIT_OPTIONAL_LOCKS=0`, `core.fsmonitor=false`, `log.showSignature=false`, `--no-ext-diff --no-textconv`, `--ignore-submodules=all` (status/diff; a submodule's own config could run programs), every configured `filter.<name>` blanked via `-c` (`_filter_overrides`: a clean/process filter runs whenever git compares the work tree with the index; it refuses to run git if the filter config output hits the cap) stdout read through a pipe and capped at `MAX_GIT_OUTPUT_BYTES` (1 MB; git runs in its own process group, killed with everything it started on the cap or `GIT_TIMEOUT_SECS`) and no pager/prompt, and refuse a `ref` starting with `-` (`--output=…` would write a file). `CliAgent._check_permission` allows `is_read_only()` tools (`tool_calls.py`; never MCP tools) without a prompt. They are the `read_only` toolset, in `_HELPER_AGENT_TOOLS` but not `TRUSTED_OUTPUT_TOOLS` (file content is untrusted).

Todo tools (`app/tools/todo.py`) keep an in-memory `TodoList` per asyncio task via a `ContextVar`: `BackgroundAgent.process_incoming()` calls `init_task_todos()` so each channel has its own list, and tool calls (child tasks from `asyncio.gather`) inherit it. Without a scope (CLI, tests) a module-level default list is used.

**Long-term memory** (`app/tools/memory.py`, store in `app/infra/memory_store.py`). `MemoryStore` keeps short facts about the user in the `memories` table of `APP_DB` (id, content, category, core, created_at, updated_at; `core` added by `ALTER TABLE` on older tables) with an FTS5 external-content index `memories_fts` (porter stemming, so "dogs" matches "dog"; a missing or older unstemmed index is (re)built in `_ensure_schema`) synced by triggers. `save()` adds a memory, replaces one when given `memory_id`, and skips case-insensitive exact duplicates (a unique index on `lower(content)` + `INSERT … ON CONFLICT DO NOTHING`, so concurrent saves can't duplicate); `delete()` uses `DELETE … RETURNING`; `search()` quotes each query word and ORs them (so user text can't inject FTS syntax), ranked by `bm25`, with a `LIKE` fallback; an empty query returns the most recent. Memories are deliberately global (one bot, one owner — like conversations, which the web UI shows across all channels): anyone allowed on any channel shares them. The agent decides what to store — guidance (what to save, never secrets, one third-person fact each, update instead of duplicate) is in `sys_instructions.md`. `get_default_sys_prompt()` appends a `## Saved Memories` section on every turn: first the **core** memories (`save_memory(core=true)`, marked ★ — name, time zone, hard constraints; `MemoryStore.core()`, up to `MAX_CORE_MEMORIES` (20) / `MAX_CORE_MEMORY_CHARS` (2500) so recent ones can't crowd them out; an update with `core` omitted keeps the setting, and re-saving a duplicate with `core=true` promotes it), then the most recently updated ones, `MAX_PROMPT_MEMORIES` (30) in all and capped at `MAX_PROMPT_MEMORY_CHARS` (6000). The lines are fenced in `<saved_memories>` tags under a note that they are user notes, not instructions, so stored text can't pose as system rules (prompt injection via a saved memory). Nothing is chosen by the current message (matching on it pulled in memories about other topics); the agent calls `search_memory` when it needs more. Best-effort: DB errors are logged and the section dropped. The store's default path is the module-level `memory_store.DB_PATH`, read at call time; an autouse fixture in `tests/conftest.py` points it at a temp file. **Core-memory guard:** `Agent.handle_tool_call()` sets `_untrusted_output_seen` (reset at the start of each `_loop()` turn) once any tool outside `TRUSTED_OUTPUT_TOOLS` (`app/core/agent.py`: save/delete_memory, calculator, get_datetime) has returned — web, search, files, bash, MCP, helper agent, `search_memory` and the todo tools (memories and todos may hold text copied from such output); after that, `_guard_core_save()` turns `save_memory(core=true)` into `core=None` (new memory non-core, existing one unchanged) and appends a note to the result, and `_refuse_core_edit()` refuses `save_memory(memory_id=…)` / `delete_memory` on an existing core memory (the id is first normalised as SQLite would read it, so "1.0" can't slip past; a save matching a core memory's text is refused too), so injected content can't plant, rewrite or remove a memory that reaches every future prompt. If the core check itself hits a database error, the call is refused (fails closed). The guard covers the memory tools only: `bash`/`write_file` could still edit `app.db` directly, which is governed by the normal tool-permission model, like any other shell action. `HelperAgent` gets `search_memory` only, and its `handle_tool_call()` refuses any tool not in `helper_tool_specs`, so an off-list call from the model can't run.

**Toolsets.** `app/core/toolsets.py` defines `TOOLSETS`, named groups of tools (names only, no imports). A member is a built-in tool name, `@<toolset>` (another group) or `mcp:<server>` (every tool of that MCP server, looked up when specs are built, via `mcp_manager.get_tools_for_server`). Groups: `read_only` (must equal the tools flagged `read_only`; tested), `files` (`@read_only` + `write_file`), `shell`, `web`, `utility`, `todo`, `memory_read`/`memory`, `schedule_read`/`schedule`, `delegate` and `helper`. `tool_calls.resolve_toolset(*names)` returns `(built-in names, MCP servers)` and raises `ValueError` on an unknown toolset or tool or a cycle; `toolset_specs(*names)` returns the specs (registry order, then MCP). Every toolset is resolved at import, so a typo fails at startup. A new agent role (e.g. a security agent: `@read_only`, `@web`, `mcp:<scanner>`) is a new entry here. `CliAgent` and `BackgroundAgent` still get every tool (`get_all_tool_specs()`).

`HelperAgent(toolsets=("helper",))` gets only its toolsets' tools (`self.tool_specs`) and its `handle_tool_call()` refuses anything else. The `helper` toolset (`_HELPER_AGENT_TOOLS` / `helper_tool_specs` in `tool_calls.py`) is used by scheduled tasks and by default: scheduled-task changes (`add/update/remove_scheduled_task`) and `helper_agent` are left out to prevent recursion, memory is read-only, and MCP tools are left out. The `helper_agent` tool takes an optional `toolset` from `HELPER_TOOLSET_CHOICES` (`app/tools/helper_agent.py`), groups within `helper` only (tested), so the model can narrow a helper's tools (e.g. `read_only`) but never widen them.

`get_all_tool_specs()` merges built-in specs with any MCP tool specs at call time (not module load). `run_tool_async()` is the async dispatcher used by `handle_tool_call` — it routes to `MCPManager.call_tool()` for MCP tools or falls through to the synchronous `run_tool()` for built-ins.

### Skills

`app/infra/skills.py`. A skill is a folder with a `SKILL.md`: a `---` frontmatter block (`name:`, `description:`; simple `key: value` lines, no PyYAML) then the instructions; extra files (e.g. `browser/scripts/snapshot.py`) sit beside it. `discover_skills()` scans `BUILTIN_SKILLS_DIR` (`app/skills`) then `USER_SKILLS_DIR` (`$ANOTHERBOT_HOME/skills`, created by `ensure_home_dir()`) on every call (no cache, so edits apply without a restart); a user skill replaces a built-in one of the same name. Without frontmatter the folder name and first prose paragraph are used; an invalid name (`NAME_RE`) or an unreadable/oversized (`MAX_SKILL_FILE_BYTES`) file is logged and skipped; descriptions are cut to `MAX_DESCRIPTION_CHARS` (300). `get_default_sys_prompt()` appends `skills_prompt_section()` (names + descriptions only, fenced in `<skills>`, capped at `MAX_PROMPT_SKILLS` / `MAX_PROMPT_SKILL_CHARS`) before the memories. The `use_skill(name)` tool (`app/tools/skill.py`, `read_only`, in `_HELPER_AGENT_TOOLS`, not in `TRUSTED_OUTPUT_TOOLS`) returns `load_skill()`: the body without frontmatter, the skill directory and its other files. `/skills` (`skills_cmd` in `commands.py`) lists them. `/<skill> [request]`: each dispatcher (`BackgroundAgent.process_incoming`, `Tui.run_command`, the plain CLI REPL) tries its registered commands first, then `skill_invocation()` rewrites the line into a prompt (`Use the "<name>" skill for this request: …`) that runs as a normal agent turn (the TUI shows what was typed via `run_turn(text, prompt=…)`). `skill_completions(registry)` adds unshadowed skills to TUI autocomplete and `/api/commands`. Tests: the autouse `isolated_user_skills` fixture points `USER_SKILLS_DIR` at a temp dir; `tests/test_skills.py` checks every shipped skill has valid frontmatter.

### MCP Servers

`MCPManager` (`app/core/mcp_manager.py`) owns persistent FastMCP client connections and their tool catalogs. It is a module-level singleton (`mcp_manager`). `initialize_mcp()` (same module, called from `main()`) reads `mcp_servers.json`, then calls `mcp_manager.initialize()` which connects all servers concurrently via `asyncio.gather`. Each server's tools are discovered via `list_tools()` and registered under the namespace `servername__toolname` (`_SEP = "__"`). `rpartition` is used when routing calls so tool names may contain underscores freely; only the server name must not contain `__`.

The singleton is shut down via `mcp_manager.shutdown()` in a `try/finally` block in `main()`. `HelperAgent` does not receive MCP tools — its default `helper` toolset has none, to prevent recursion.

### System Context

On startup, `load_system_context()` (`app/infra/startup.py`) loads `app/core/sys_instructions.md` and prepends it as the system message to `self.messages`.

### Tracing

`--trace` (or `/trace on`) turns on LLM call tracing to `--tracedir` (default `$ANOTHERBOT_HOME/trace`). Each agent owns a `Tracer` (`app/infra/tracer.py`) that keeps one line-buffered JSONL file open per conversation (`trace_<label>_c<conv_id>_<ts>.jsonl`; `helper` agents get one file per run) and rotates it when the conversation or trace dir changes or tracing is toggled. `start_turn()` is the only place a file is opened (`record()` is a no-op without one, so a turn that began with tracing off is never half-traced); `/trace off` goes through `tracer.set_tracing(False)`, which closes every open trace file, and `main()` calls `tracer.close_all()` on shutdown. Tool results are recorded as each call finishes, not after the whole `gather` batch. Events are appended as they happen: `session` (always the first line), `history` (messages the model already had when the file was opened), `turn_start` (system prompt + user message), `llm_response` (serialized assistant message incl. tool calls/reasoning, usage, latency, finish reason), `tool_result` (with duration), `no_choices`, `stopped`, `turn_end` and `error` (recorded by `Agent._loop` before re-raising). Base64 attachment data URLs are redacted. Tracing failures are logged, never raised.

### Runtime Settings

`app/core/runtime.py` is an in-memory key-value singleton (`set()` / `get()`) for mutable settings like `model`, `base_url`, and `max_iterations`. Values are populated from `config` (env vars) during startup in `main.py` and can be changed at runtime via the `/model` slash command.

### Channels & Command Registry

**Channel types** are defined in `ChannelType` enum (`app/channels/channel.py`): `CLI`, `TELEGRAM`, `DISCORD`, `WEB`. Each channel implements the `Channel` ABC and owns a `MessageQueue` instance. `bg_server.py` wires up enabled channels — each gets its own `MessageQueue`, `BackgroundAgent`, and set of coroutines (`run_polling`, `process_incoming`, `process_outgoing`) gathered into the event loop.

**WebChannel** (`app/channels/web_channel.py`) is a plain Starlette app served by uvicorn: a JSON HTTP API plus a JSON WebSocket endpoint (`WS /ws`) on the same port. The browser UI is static HTML/CSS/JS in `app/channels/frontend/` (`index.html`, `app.js`, `app.css`, `login.html/js/css`, `vendor/`; no build step), located via `FRONTEND_DIR` and served by a catch-all `Mount("/", StaticFiles(html=True))` registered after the API routes; every frontend response carries `Cache-Control: no-cache` (revalidated via ETag) so edits show up on reload without version query strings. The frontend talks to the server only through HTTP JSON and WebSocket frames — no server-side templating. Multiple concurrent browser tabs are supported — each connection gets a UUID tracked in `_connections`. A per-connection `asyncio.Lock` in `_send_locks` serializes writes to each WebSocket. The channel exposes `GET /api/conversations`, `GET /api/messages` (`load_messages(..., with_meta=True)`: each message also has its row `id` and `has_trajectory`), `GET /api/messages/{id}/trajectory` (a turn's trajectory as a JSON download, 404 if none), `GET /api/status` (`{"model", "auth"}` — the header shows `model` as a button that pre-fills `/model `, refreshed on connect, after system messages and at each turn start since the model is shared across channels; `auth` tells the UI whether to show the logout button), `GET /api/commands` (the agent's `CommandRegistry` — `bg_server` sets `web_channel.commands = web_agent.registry` — plus the channel-handled `/whoami`, sorted; drives the input's slash-command autocomplete, which after `/load|fork|rename|export|delete ` suggests conversations from the last `/api/conversations` list), `POST /api/upload`, and the sidebar's per-conversation `⋯` actions: `POST /api/conversations/{id}/rename` (JSON `{"name"}`; done over HTTP rather than `/rename` because slash commands queue behind a running agent turn) and `GET /api/conversations/{id}/export` (a JSON download built by `ConversationStore.export_payload()`; nothing is written server-side). Fork has no endpoint — it needs the agent to switch conversations, so the sidebar sends `/fork <id>` over the WebSocket like `/load`. `ConversationStore.fork()` names the copy `"<name> (fork)"`, then `(fork 2)`, … (forking a fork bumps the number instead of stacking suffixes); an unnamed `"New Conversation"` keeps its name so auto-naming still applies. Delete likewise goes over the WebSocket as `/delete <id>` (two-click confirm in the menu; disabled for the active conversation while a turn is running, since the command would queue behind it): `delete_conversation_cmd` refuses a conversation that another channel has active (`conversation_id:<ch>` runtime key — that agent would keep writing to the deleted ID; `MessageHistory` writes don't enforce FKs), and deleting the agent's own active conversation switches it to the channel's most recently updated remaining one (`get_last`, as on startup) or a new one if none is left; `app.js` (`handleDeleteReply`) reads the switched-to ID from that reply, loads its messages and shows the reply below them. `ConversationStore.delete()` removes the messages and row in one transaction and nulls forks' `parent_id` first (FKs are enforced). Rename goes through `rename_conversation()` in `commands.py` (shared with `/rename`), which also refreshes the cached `conversation_name` runtime key of every channel that has that conversation active. `app.js` parks sidebar refreshes while an actions menu or rename box is open (`sidebarBusy()`), since re-rendering would destroy them. The web UI is an admin interface. Auth lives in `app/channels/web_auth.py`: when `WEB_PASSWORD` is set, `WebChannel.start()` wraps the Starlette app (`_app`) in `WebAuthMiddleware` (pure ASGI, so it also guards the `/ws` handshake) and uvicorn serves `_asgi_app`. The middleware handles `POST /api/login` (JSON `{"password"}` → `{"ok": true}` or 401 `{"error"}`) and `POST /api/logout` itself, issues a signed `HttpOnly`/`SameSite=Lax` cookie (itsdangerous `TimestampSigner`, key derived from the password, 30-day max age), lets `GET /login`, `/login.css`, `/login.js` through unauthenticated (a logged-in `/login` redirects to `/`), redirects `GET /` to `/login`, returns 401 for every other HTTP path (API and frontend files), rejects unauthenticated WebSocket handshakes, and rejects cross-origin WebSocket handshakes and non-GET requests (`Origin` host must equal `Host`). `/login` is 404 when no password is set. Without a password, `start()` raises `RuntimeError` unless the host is loopback; `bg_server` catches it, logs, and skips only the web channel. Tests use `TestClient(ch._asgi_app)`. Because it is an admin view, `/api/conversations` calls `ConversationStore.list()` with no channel and returns conversations from **all** channels (each row includes `channel`, rendered as a badge in the sidebar), and `/api/messages` serves any existing conversation (404 only if the ID does not exist). `POST /api/upload` accepts multipart `files` (one or more), writes each under `$ANOTHERBOT_HOME/uploads` with a UUID prefix, and returns the stored basenames; the browser (paperclip button next to the input, or pasting files into the message box — skipped when the clipboard also has plain text, e.g. spreadsheet cells; generic `image.png` screenshots are renamed `pasted-<local timestamp>.png`) sends those basenames back in the WebSocket `message` frame's `files` field. `_resolve_upload_paths()` joins each basename to the upload dir (basename-only, so client paths can't traverse out) and the resolved absolute paths reach the agent via `metadata["files"]`, which `Agent._build_user_message()` encodes as image/file parts. History keeps them as `[Attachment: <stored name>]` markers (`_build_placeholder_content`); `app.js` parses those out of user messages (live-sent ones are rendered from the same markers) and shows raster images as thumbnails that open a lightbox, other files as download chips with the UUID prefix stripped. `GET /api/uploads/{name}` serves them: basename-only via `_resolve_upload_paths`, png/jpeg/gif/webp inline, everything else (SVG/HTML included) as an `application/octet-stream` attachment, always with `nosniff` + `Content-Security-Policy: default-src 'none'; sandbox` because uploads share the UI's origin and session cookie. Markers whose file isn't in the upload dir (e.g. CLI attachments) fall back to a plain, unlinked chip. Bot replies render as markdown by default via vendored `app/channels/frontend/vendor/marked.min.js` + `purify.min.js` (DOMPurify sanitizes the HTML; no CDN); a header **Markdown | Raw** switch re-renders every reply from the original text kept in `bubble.dataset.raw` and is remembered in `localStorage` (`ab-render`). Each reply row also gets a **Download trajectory** button (stacked under the copy button in `.msg-actions`) when it has a stored trajectory: history replies use `has_trajectory`, and for live turns `WebChannel.on_trajectory_saved` sends a `{"type":"trajectory","message_id","conversation_id"}` frame (through the outgoing queue, like every turn frame) after the turn's last reply, which `app.js` attaches to that turn's last reply row (`turnReplyRow`, reset on each `busy: true`). Each reply row also gets a copy button (appended to the row, not the bubble, since re-rendering replaces the bubble's HTML) that copies `dataset.raw`; it falls back to a hidden textarea + `execCommand('copy')` because the Clipboard API only exists in secure contexts and the UI is often opened as plain `http://<lan-ip>`. `/whoami` (needs the per-connection client ID) and `/stop` are handled inline. `/stop` must not go through the message queue: `BackgroundAgent.process_incoming()` handles one item at a time, so a queued `/stop` would only run after the turn it should stop (and then poison the next turn). It sets `stopped` only while a turn is running ("Nothing to stop." otherwise); the loop checks it between steps. Turn state comes from the `Channel.on_agent_turn(running)` hook (no-op by default), which `process_incoming()` awaits around each `agent_loop()` (after `clear_stopped()`, so a stale idle `/stop` never cuts a turn short); `WebChannel` overrides it to enqueue `{"type":"busy","busy","stopped"}` frames on the outgoing queue (addressed to the channel object, which is what `MessageQueue` routes by) so they stay ordered after the turn's replies, broadcasts them to every tab, and sends the current state on connect. The UI drives the thinking dots and a Stop button ("Stopping…" until the turn ends, then "Stopped.") from those frames. **Turn frames carry the conversation.** `process_incoming()` adds `conversation_id` to a turn's metadata (thinking text, tool status, reply, error, trajectory), and busy frames carry the turn's conversation (the `conversation_id:web` runtime key at turn start). `WebChannel.send_message()` broadcasts every turn frame to all tabs (they share one agent; the tab that sent the message may have been closed) — only command replies (`is_command`) stay with the requesting tab. It also records, as frames are *delivered*, the last busy frame (`_shown_busy`) and the running turn's frames (`_turn_frames`, capped at `_MAX_TURN_FRAMES`); a connecting tab gets those first, under its send lock so live frames queue behind the replay. In `app.js`, frames that arrive while the chat is loading from the server wait in `holdFrames()` and are handled on top of the history (a replayed final reply already in the history isn't shown twice); turn frames for a conversation the tab isn't showing are dropped; a `busy: true` for a turn this tab didn't start (or in another conversation) reloads that conversation from the history. While a turn runs or is pending (`switchLocked()`), conversation switching is blocked: sidebar clicks, **+ New**, the **Fork** menu item and typed `/new`, `/load`, `/fork` — those would queue behind the turn and its replies would land in the wrong conversation. All other slash commands — including `/help`, `/status` — are forwarded to `BackgroundAgent`'s `CommandRegistry` via the message queue with `is_command=True` in metadata so `send_message()` emits `{"type":"system"}` responses, enabling the sidebar to refresh after conversation-mutating commands.

**Slash commands** are handled entirely by `BackgroundAgent`. Channel handlers (`command_handler` in Telegram, `on_message` in Discord) intercept only `/whoami` (resolved inline using the platform user object) and `/stop` (sets the channel's `stopped` flag immediately, as the web channel does), and enqueue everything else as a plain `IncomingMessage`. `BackgroundAgent.process_incoming()` detects the leading `/` and dispatches via its own `CommandRegistry`. That registry owns the full command set: `/model`, `/status`, `/stop`, `/restart`, `/help`, `/list`, `/new`, `/load`, `/fork`, `/rename`, `/export`, `/delete`, `/mcp`, `/skills` (plus `/<skill>` for each skill). Both `BackgroundAgent` and the CLI build it with `build_command_registry()` (`app/channels/commands.py`); the bot adds `/stop` via `extra=` — only so `/help` lists it: every channel answers `/stop` itself, and the registry handler (which could only run between turns) just replies "Nothing to stop." without setting the flag. Conversation commands use the agent through the `ConversationAgent` protocol (`store`, `channel_str`, `conversation_id`, `switch_conversation()`). `/list` is scoped to the caller's channel, but `/load`, `/fork`, `/rename` and `/export` accept any conversation ID regardless of which channel created it — `ConversationStore.rename/fork/export` no longer enforce channel ownership (`fork` creates the copy under the caller's channel).

### Restart

`/restart` (a `BackgroundAgent` command) and `SIGHUP` (sent by `restart.sh`) call `restart.request_restart()` (`app/infra/restart.py`). The SIGHUP handler is a plain `signal.signal` handler (`install_sighup_handler()`, not `loop.add_signal_handler`, which reverts to the fatal default when the loop closes) and stays installed through shutdown; `exec_restart()` sets SIGHUP to `SIG_IGN` before `execv` so no second HUP can kill the bot mid-restart. While a restart is pending nothing new starts: `process_incoming()` answers non-command messages with "Restarting, please send that again…" and `ScheduledTasks.run()` skips due tasks. `start_server()` waits (up to 300 s) for running turns — `process_incoming()` wraps each `agent_loop()` and `ScheduledTasks.run_task()` wraps each run in `restart.turn()` — and for every `MessageQueue` to be `outgoing_idle()` (queue empty and no delivery in flight), then cancels the channel tasks (waiting on each one, so uvicorn closes WebSockets with 1012) and returns. A scheduled run cancelled anyway is recorded as `cancelled` and keeps its slot. After the asyncio runner closes, `app/main.py` calls `restart.exec_restart()`: `uv sync --frozen --no-dev --inexact` (mirrors the image build), chdir back to the start directory, `os.execv(sys.orig_argv)`. The PID stays the same on purpose: killing the main process breaks Docker (PID 1) and supervisors that kill the process group, taking the restart script with it.

`start_server()` writes the Python PID to `$ANOTHERBOT_HOME/background.pid` on every start. `restart.sh` detaches (`setsid nohup`, log in `$ANOTHERBOT_HOME/restart.log`), sends SIGHUP to that PID, then waits for the PID file's mtime to change (restarted) or the PID to exit (then it starts a new bot). If there is no valid PID file, it treats the bot as a pre-restart build: it finds it via `/proc` (the Docker image has no `ps`/`pgrep`), matching only a Python `app.main … background` process whose cwd is this data dir's `workspace`, stops it with SIGTERM and starts a new one.

### Message Queue

`MessageQueue` (`app/channels/message_queue.py`) holds two `asyncio.Queue`s (incoming/outgoing). `BackgroundAgent.process_incoming()` consumes the incoming queue and drives `agent_loop()`; `process_outgoing()` dispatches outbound messages to registered delivery functions.

Each channel **must** have its own `MessageQueue` instance to avoid cross-channel message routing bugs.

### Scheduled Tasks

`ScheduledTasks` (`app/core/scheduled_tasks.py`) is a SQLite-backed task runner using the shared `APP_DB` (`$ANOTHERBOT_HOME/app.db`, default `~/.anotherbot/app.db`). It polls every 30 seconds, checks `next_run`, and executes due tasks via `HelperAgent`. Results are delivered to the configured channel via `MessageQueue`. Schema: `tasks` (id, name, prompt, enabled, repeat, interval_mins, next_run, last_run, delivery_channel, run_count, created_at) and `task_outputs` (id, name, prompt, output, status, duration_secs, timestamp). The `run()` coroutine is added to the `asyncio.gather` in `bg_server.py`.

## Linting

`uv run ruff check app tests`, `uv run ruff format app`, and `uv run pylint app` (pylint is a dev dependency; run it via `uv run` so it sees the project venv). Deliberate exceptions are marked inline with `# pylint: disable=<rule>  # reason` — e.g. broad `except Exception` at boundaries where errors are returned to the model or a loop must keep running, and lazy imports that break import cycles.

## Testing Approach

Unit tests mock `app.core.agent.Client` and `load_system_context` to isolate the agent loop logic. `run_tool` is patched at `app.core.tool_calls.run_tool` (where the function lives) since `handle_tool_call` uses a lazy import. Integration tests in `tests/integration/` mock only the OpenAI HTTP client and run the full pipeline including `main()`, argparse, and agent construction. Tests use `pytest-asyncio` for async test functions.

Config is env-only, so tests set it with `monkeypatch.setenv(...)` and call `config.load()`. The autouse fixture in `tests/conftest.py` clears every config env var (`CONFIG_ENV_VARS`) and restores `config._config` around each test, so the developer's shell or `.env` never leaks in — add new config env vars to that list.
